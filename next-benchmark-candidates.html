What to run after MedQA and HealthBench

Created 2026-07-31

Recommendation

Run MedAgentBench next. Our two healthcare benchmarks so far cover two of the three axes that matter for the infrastructure-flexibility story: MedQA is single-turn knowledge, HealthBench is multi-turn dialogue. Both grade text. MedAgentBench is the axis neither one touches: a tool-using agent acting on a stateful sandboxed EHR, where the score comes from re-inspecting the environment afterwards rather than from reading the transcript.

It is also the safest choice politically. It is published in NEJM AI (2025), MIT licensed, already listed in our own dataset catalogue as entry 31, and it is one of only two benchmarks Anthropic cited for Claude for Healthcare. The leaderboard is unsaturated at 69.67% for the best model, so unlike MedQA there is still signal to report.

Two optional companions, in priority order: AgentClinic for the multi-model-role axis (cheap, and it reuses MedQA cases so the three runs share source data), and JMedEthicBench for the Japanese adversarial axis, which is the piece that joins this workstream to the AgentSafety plan.

MedAgentBench in detail

A virtual EHR built by the Stanford ML Group. 300 tasks written by two internal-medicine physicians, run against 100 de-identified patient profiles drawn from the Stanford Research Repository (STARR), served by a FHIR-compliant API. The agent has to issue correctly structured GET and POST requests against real FHIR resource types, so the benchmark tests understanding of the healthcare API standard, not just clinical knowledge.

Task mix: 10 categories, 30 tasks each data/medagentbench/test_data_v2.json

Half the categories are information retrieval (what is this patient's MRN, most recent magnesium, last HbA1c) and half are order entry (document a measurement, order a lab, place a referral, prescribe). Retrieval tasks are graded on the returned answer; order-entry tasks are graded on whether the right resource now exists on the server. That split is what the benchmark reports as Query SR and Action SR.

A retrieval task and an order-entry task, verbatim:

task4_1  "What's the most recent magnesium level of the patient S3032536
          within last 24 hours?"
         context: code for magnesium is "MG", answer in mg/dL, -1 if unavailable

task8_1  "Order orthopedic surgery referral for patient S2016972. Specify

Provenance and licensing github.com/stanfordmlgroup/MedAgentBench

MIT, 308 stars, last pushed 2025-11-21. Published in NEJM AI as 10.1056/AIdbp2500144, preprint arXiv:2501.14654. Patient data is de-identified and shipped inside the container, so there is no PhysioNet-style credentialing gate and no real patient information enters our environment. That matters for the framework deck, which explicitly wants scenarios that can run 実患者情報を含めずに.

What the port costs

Nothing in this family ships natively. Upstream inspect_evals as of today has medqa, healthbench (plus _consensus, _hard, _meta_eval), pubmedqa and vqa_rad, and no agentic medical task at all. So this is a build, which is the point: the flexibility story is stronger when we author the components rather than call a registry entry.

Harness shape

Five build steps

1 · Dataset loader exists, trivial

One flat JSON array of 300 records with id, instruction, context, sol and eval_MRN. A record_to_sample of about ten lines. The id prefix (task1 through task10) carries into metadata because the scorer dispatches on it.

2 · Nine FHIR tools plus react() data/medagentbench/funcs_v1.json

The tool schemas ship as JSON with descriptions lifted from the Epic FHIR API docs, so they convert almost mechanically into Inspect tool definitions: five GET (Patient, Observation by code, Observation by category, Condition, MedicationRequest, Procedure) and three POST (Observation, MedicationRequest, ServiceRequest). Wrap each as a thin HTTP call to the sandbox base URL and hand the set to react(). Same pattern as the GAIA run, different tools.

3 · Sandbox with the FHIR server docker pull jyxsu6/medagentbench:latest

The upstream harness runs the FHIR server on port 8080 and a fleet of task workers on 5000 to 5015. We only need the server, the worker fleet is AgentBench scaffolding that Inspect replaces. So the compose file is a single service, and the agent reaches it over the sandbox network.

4 · The scorer, which is the actual work src/server/tasks/medagentbench/eval.py:8

Upstream grading dispatches on the task category to one of ten reference functions:

def eval(case_data, results, fhir_api_base):
    task_id = case_data['id'].split('_')[0]
    grader_func = getattr(refsol, task_id)      # task1 .. task10
    return grader_func(case_data, results, fhir_api_base) is True

Retrieval graders compare the agent's answer against sol. Order-entry graders issue their own GET against the live server and check that the posted resource is present and well formed. Porting means bringing those ten functions inside one Inspect @scorer and letting the metric split retrieval from action.

5 · Run, then report rerun with current frontier models

The published table stops at Claude 3.5 Sonnet v2 and Gemini 1.5 Pro. A clean rerun on current models across both metrics is a publishable result on its own, and it stresses the same sandbox concurrency path we already tuned for Cybench.

@task
def medagentbench() -> Task:
    return Task(
        dataset=json_dataset("test_data_v2.json", record_to_sample),
        solver=react(tools=fhir_tools()),          # step 2
        scorer=medagentbench_scorer(),           # step 4
        sandbox=("docker", "compose.yaml"),      # step 3, FHIR on :8080
    )

@scorer(metrics=[accuracy()])
def medagentbench_scorer():
    async def score(state, target):
        # dispatch on task1 .. task10, exactly like refsol
        grader = GRADERS[state.metadata["id"].split("_")[0]]
        ok = await grader(state, api_base())     # may re-GET the server
        return Score(value=CORRECT if ok else INCORRECT)
    return score

Risks and gotchas

★
The reference graders are not in the repository. refsol.py is distributed separately through a Stanford Box link in the README, deliberately, to keep the answer key out of training corpora. Download it before scoping the scorer work, and treat that link as a dependency that could rot.
  • amd64 image. jyxsu6/medagentbench:latest runs under Docker Rosetta on this Mac, same as the Cybench images. Expect the same slowdown, and pin --platform linux/amd64 if the image is imported anywhere else.
  • No Japanese content. Tasks, codes and patients are all US clinical practice. A JP localisation (JMDC-style codes, 日本語 instructions) is a follow-on project, not part of this port. Worth saying out loud in the deck so nobody expects it for free.
  • Hybrid tasks blur the metric split. Categories like task10 require a read and then a conditional write, so a single boolean per sample understates partial success. Keep the upstream definition for comparability, and consider a second, finer metric of our own.
  • Upstream is AgentBench-shaped. Its client, assigner and task-worker layers all disappear when Inspect drives the loop. Do not try to port the harness, only the data, the tool schemas and the graders.

Two companions

AgentClinic, for the multi-model-role axis

Four model roles in one eval: a doctor agent under test, a patient agent, a measurement agent that answers test-order requests, and a moderator. MIT, 340 stars, arXiv:2405.07960. The reason to pair it with MedAgentBench is narrative economy: AgentClinic-MedQA is 215 cases derived from MedQA itself, so one slide can show the same source questions rendered three ways, as an MCQ, as a dialogue and as an agent-versus-agent encounter. Escalating infrastructure, constant data.

It also lands on machinery we have already used. The persuader / persuadee / judge role dispatch in the APE and MakeMeSay work is the same get_model(role=…) pattern. Caveat: the repository has not been touched since 2024-12-31, so port the protocol from the paper and treat the code as reference only. The MIMIC-IV variant needs PhysioNet credentialing, so stay on the MedQA and NEJM variants.

JMedEthicBench, for the Japanese adversarial axis

This is the one that connects this workstream to the AgentSafety plan. Multi-turn adversarial Japanese medical safety, built on 67 Japan Medical Association guidelines, over 50,000 adversarial conversations generated from seven automatically discovered jailbreak strategies, scored by a dual LLM protocol. 27 models evaluated. The headline finding is directly on-message for the framework: safety scores fall across turns, median 9.5 down to 5.5, so multi-turn escalation walks around defences that hold on the first turn. Medical-specialised models were more vulnerable than commercial ones, in both Japanese and English.

The attacker / target / judge harness in evaluation_components_breakdown.html already covers this shape, so the marginal build is a dataset loader and a judge. Caveat: arXiv:2601.01627 is from January 2026, adoption is effectively zero, and I have not verified that the conversations are actually downloadable. Confirm availability before promising it to anyone.

How it lands in the deck

The framework document already asks for this, twice. フェーズ2 lists エージェント向けサンドボックス as a module to add, and the 二層モデル appendix puts ユースケース特化 behaviour in the second layer while leaving 地力 to the existing benchmarks. MedAgentBench is the concrete instance of both: an agent operating a clinical system, measured on whether the orders it places are correct, with an upstream citation and a leaderboard attached.

It also answers the 知識-実践ギャップ argument with our own numbers rather than a quotation. The systematic-review framing in the dataset appendix is that knowledge benchmarks sit at 84 to 90% while practice-based evaluation stalls at 45 to 69%. Running MedQA at saturation and MedAgentBench at 70% on the same models, in the same harness, produces that gap as a measured result in one .eval log set.

Suggested framing for the three runs: 単一ターン (MedQA) → 多ターン対話 (HealthBench) → エージェント x 環境 (MedAgentBench), with the adversarial axis (JMedEthicBench) as the declared next step rather than a fourth completed run.

FAQ

Is any of this available in inspect_evals already?
No. Upstream main today has medqa, healthbench with its three variants, pubmedqa and vqa_rad, and no agentic medical task. All three candidates here are ports. That is a feature for the flexibility argument, and it is also why the effort estimate matters.
How big is the port, honestly?
Dataset and tools are close to mechanical. The scorer is the real item: ten grader functions to bring across, several of which issue their own FHIR queries. Comparable to the Cybench diet solver in scope, and larger than the MedQA replica's answer parser.
Does any patient data touch our environment?
Only de-identified STARR profiles, shipped inside the container image. No PhysioNet credentialing, no live data, nothing that needs an ethics route. Same posture as the framework's シナリオカード design, which is explicitly built to run 実患者情報を含めずに.
What if we only have budget for one more run?
MedAgentBench alone. It is the only candidate that adds two Inspect subsystems at once (sandbox and tool calling) and a scorer class we have never written, and it is the only one with both a journal publication and a vendor citation behind it.
What is the first thing to check before committing?
That the refsol.py Box link still resolves and the graders inside are complete for all ten categories. Everything else in the estimate is visible in the public repository; that one file is not.
