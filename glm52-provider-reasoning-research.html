GLM 5.2 across providers: does the API path change reasoning?

Created 2026-08-06

We ran GLM 5.2 on ExploitBench twice on an identical config, changing only the provider path: once through OpenRouter (pinned to the Z.AI upstream) and once through the direct Z.ai API. Capability scores came out nearly the same, but the OpenRouter run spent ~1.5x the reasoning tokens. We suspected the shared setting reasoning_effort=max might resolve to a higher effort mode on one path than the other. A controlled probe says it does not: at max, the two paths reason essentially equally (11,375 vs 11,085 tokens on a fixed prompt). The eval's 1.5x gap sits inside normal single-seed sampling noise. Along the way we found something actionable: max is not GLM 5.2's top reasoning tier, xhigh is, so both eval runs under-shot the model's real ceiling.

1 · What the initial evals showed

Both runs used the same v8-bench contract: all 41 bugs, seed 1, nudges off, 300-turn budget, temperature=1.0, reasoning_effort=max. The only intended difference is how the model was served.

Capability was basically a tie. Mean capability 2.54 (OpenRouter) vs 2.80 (direct) on the 16-flag scale; 26 of 41 bugs scored identically; the handful of large per-bug swings are the kind of thing a single seed at temperature 1.0 produces.

Reasoning spend was not a tie. On near-identical turn counts, the OpenRouter run emitted about 1.5x the reasoning tokens.

2 · What we suspected

Both configs literally sent the string reasoning_effort: max. But that parameter is not standardized across the two paths, so "max" might not mean the same thing on each:

  • Z.ai native: GLM 5.2 has thinking on by default, toggled by a thinking: {type: enabled/disabled} object; effort levels (High / Max) are model-side, Max recommended for coding.
  • OpenRouter: for GLM 5.2 it documents high and xhigh, and states xhigh maps to max reasoning. max is not its canonical token.

So the working hypothesis: the OpenRouter eval may have effectively run a higher reasoning mode than the direct API, which would make the 1.5x gap a configuration artifact rather than a property of the model or the provider's serving stack. If GLM 5.2 exposes two effort modes roughly 1.5x apart, we wanted to know which one each path actually used. A secondary question: can our logs even show what Z.ai did when reached through OpenRouter?

3 · What we did

Log forensics: what our transcripts actually capture transcript.jsonl

Every model turn stores content, the full reasoning_content (chain-of-thought text), per-turn usage token counts, stop_reason, served_model, and provider_response_id. We verified the CoT capture is not lossy: of the direct run's 11,800 turns, exactly the 1,047 turns with reasoning_tokens > 0 also carry stored reasoning text, no billed-but-dropped reasoning. Provenance is unambiguous: served_model reads zai/glm-5.2 vs z-ai/glm-5.2, and the response id is a Z.ai hex id vs an OpenRouter gen- id, so every turn is attributable to its path.

Controlled probe: sweep reasoning_effort on both paths scripts/probe_glm52_reasoning_effort*.py

One fixed hard prompt (a 32-term inclusion-exclusion count), temperature=1.0, max_tokens=24000, 3 reps per setting. We swept <default>, low, medium, high, max, xhigh on each path and read realized completion_tokens_details.reasoning_tokens. OpenRouter was pinned to the z-ai upstream (order=[z-ai], allow_fallbacks=false) to match the eval. The original direct key was out of balance (the same depletion that pushed the eval onto OpenRouter mid-run), so the direct arm used a fresh Z.ai key.

Raw-response check: what OpenRouter exposes about the upstream openrouter/api/v1

We inspected a raw OpenRouter response. It returns the reasoning text (reasoning + reasoning_details), the reasoning_tokens count, provider: "Z.AI", and even upstream_inference_cost. It does not expose Z.ai's literal response body or the internal effort tier Z.ai applied. So effort can only be inferred from realized reasoning-token volume, not read off a field.

The exact parameters each path received, and what OpenRouter hands back:

# glm52-zai-direct-bundle/.../config_snapshot.yaml

4 · What we found

The decisive row: at max, the two paths are equal

Sweeping the full ladder (mean realized reasoning tokens, 3 reps):

reasoning_effortOpenRouter → Z.AIdirect Z.ai
<default> (omitted)6,41214,959
low8,7575,608
medium6,5095,934
high5,4727,112
max  (eval used)11,37511,085
xhigh  (true max)15,92913,973

At max, the exact value both eval runs sent, the two paths land within 3% of each other (11,375 vs 11,085). So max does not map to different effort tiers across providers, and the hypothesis is not supported. The eval's 1.5x reasoning gap is therefore not a reasoning_effort mapping artifact; it is consistent with run-to-run sampling noise (temperature 1.0, single seed, divergent agent trajectories, different host and date). Measured within-setting variance in this probe is about 2x, and the eval gap sits inside that envelope.

max is not the ceiling, xhigh is

On both paths, xhigh produced clearly more reasoning than max (OpenRouter ~15.9k, direct ~14.0k, versus ~11k at max), and OpenRouter's xhigh cluster was tight (15.4k to 16.9k), the most reproducible point on the whole grid. This matches the docs: xhigh maps to max reasoning, and max is a non-canonical token that resolves to a mid tier. Both eval runs under-shot GLM 5.2's real maximum reasoning.

One more provider difference, irrelevant to these evals but worth knowing: the defaults diverge sharply. Direct Z.ai with effort omitted reasons heavily (~15k, thinking-on-by-default), while OpenRouter's default is ~6.4k. If a future config ever omits reasoning_effort, the provider choice would matter a lot.

★
For runs that intend maximum reasoning, send reasoning_effort=xhigh, not max, on both the direct and OpenRouter paths. Both prior GLM 5.2 evals ran below the model's ceiling.

FAQ

Does this change the GLM 5.2 vs Opus conclusion?
No. Capability was a near-tie between the two provider runs regardless (mean 2.54 vs 2.80), and both sit a clear tier below Opus 4.8 (5.22). The reasoning-token gap was a process question, not a scoring one: score is the max across grade calls, so extra reasoning did not buy points.
Can we prove there is zero provider effect at max?
No, and we do not claim that. With 3 reps against ~2x variance, the probe rules out the large, tiered difference the hypothesis needed, but cannot exclude a modest (< ~1.3x) systematic offset. A tighter number needs more reps or a lower temperature at just max and xhigh.
Can we see Z.ai's raw output through OpenRouter?
Partly. OpenRouter returns the reasoning text, token counts, provider: "Z.AI", and upstream cost, so we see how much Z.ai reasoned. It does not return Z.ai's literal response body or the effort tier Z.ai internally applied, so the effort level is inferred from token volume.
